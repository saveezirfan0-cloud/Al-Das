# Phase 20h notes: generic HTTP SMS gateway and Meta MM Lite (rest of parity gap G12)

Closes what `docs/20_SANOFLOW_REA_PARITY.md` §4 row **G12** left open after Phase 20e (`docs/27_PHASE_20E_CHANNELS_NOTES.md`): a **generic HTTP SMS provider** and **Marketing Messages Lite (MM Lite)**. Lean slice, built in a cloud sandbox with plain Postgres 16 and PostgREST, no browser and **no real provider**: the SMS gateway and Meta are fake `fetch` functions answering with shapes written from documentation. `tests/setup.ts` now also makes any `fetch` to a reserved `*.example` host or to `example-gateway.com` (the settings form's placeholder) throw; Meta's Graph host was already blocked.

**Both are OFF by default.** The generic gateway is a second provider of the existing SMS fallback integration (still `ENABLE SMS`); MM Lite is a new catalogue entry `wa_mm_lite` with its own typed words `SEND MARKETING THROUGH MM LITE`. Both are switched on under Settings, Integrations by someone with `integrations.manage` (Admin only), audited like every integration switch. **No migration, no new table, no new permission, no new environment variable.**

## What exists

| Item | Where | What it does |
|---|---|---|
| **Generic HTTP SMS provider** | `lib/integrations/sms/http.ts` (adapter), `http-config.ts` (pure settings, validation, body template), `provider.ts` (factory branch) | A second `SmsProvider` next to the Twilio-style one. Settings: the gateway's **https address** (only that host is allowed; no IP literal, internal or single-label name, no query string, no credentials, standard port), **sign-in** (bearer token, or HTTP Basic user name + password; the token/password is the secret field `gateway_secret`, AES-256-GCM in `config_enc`), **body format** (JSON or form encoding) and a small **body template** of `name=value` pairs separated by `&`: each value is `{to}` (E.164 with +), `{from}` (the registered sender ID), `{text}` (the fixed reminder wording) or a short fixed word (≤ 60 letters, digits, space, `_ . : + -`). `{to}` and `{text}` exactly once, `{from}` at most once, at most 12 fields, flat object of strings. Optional **message id field** (dotted JSON path such as `data.message_id`) and optional **check address** (GET, same host) for Test connection. Every request goes through `createIntegrationClient()` (provider name `sms_http`): no redirects, timeout, response cap, back-off, the stored breaker, one `integration_calls` row per attempt with provider, operation, outcome, status, latency and attempt only |
| **Never sent twice** | `http.ts` | The send is a POST without an idempotency key: the shared client retries it only after a 429. A timeout or 5xx is `ambiguous`; `processSmsJob` then marks the row failed (`unknown_delivery`) and never sends it again (the Phase 19a rule). When a message id field is configured, a 2xx without that field is also treated as ambiguous (`no_message_id`), because some gateways answer 200 with an error body. 4xx is a plain failure (`http_<status>`, `auth` for 401/403) |
| **Test connection** | `verify()` in `http.ts`; message in `app/(app)/settings/integrations/actions.ts` | Only a GET to the optional check address on the same host (for example the account balance). Without one, Test connection sends nothing and says there is no safe test (a test send would text someone). It never POSTs |

The settings page hides the receipt address for this provider |
| **No receipts for the generic gateway** | `lib/integrations/sms/receipts.ts` | The receipt route verifies Twilio signatures only; for an SMS account whose provider is not `twilio` it answers like a bad signature (401) whatever is posted. Rows from the generic gateway stay `sent` |

## Decisions

1. **The generic gateway is a provider option of the existing SMS fallback**, not a new integration: one switch, one daily cap, one rate limit, one fallback path. SMS stays reminder-fallback only (`smsDecision` still refuses marketing; nothing new can queue an SMS).
2. **Fixed, flat request.** No headers beyond Authorization / Content-Type / Accept, no nested JSON, no number or boolean types, no free text in the template. A gateway that needs a key in the URL, a custom header, nested JSON or a number without `+` is not supported by this lean version; that is a follow-up (a `{to_digits}` placeholder or a custom header name would be small additions to `http-config.ts`).
3. **No query string allowed in the address**, so a key can never sit in plain `config` or anywhere near a log. Keys go in the encrypted token field.
4. **Host safety** is a name check (public-looking host, https, port 443) plus the shared client's exact-host allow-list and no redirects. A public name that resolves to a private address is not detected (no DNS check); only an administrator can set the address.
5. **No delivery receipts or opt-out signal** from the generic gateway: there is no common format. The SMS stays `sent`; the reception call task raised by the failed reminder remains the safety net.
6. **MM Lite as a catalogue entry, not a channel setting**: one workspace-wide switch with typed words and the standard audit, no migration. It applies to every WhatsApp number of the workspace. Only campaign messages use it, because MM Lite is for marketing sends and a one-off template from the inbox is a conversation, not a campaign.
7. **No automatic fallback** from MM Lite to `/messages` on an error: a failure is a normal Meta error on that message (retryable ones retry, others fail and show the reason). If the WABA is not onboarded, campaign marketing messages fail until the switch is turned off (the consequence text says so).

## How an administrator switches each on

- **Generic SMS gateway:** Settings, Integrations, SMS fallback: provider "Other gateway (generic HTTP)"; enter the gateway address, sign-in (bearer token, or user name + password), body format, body fields such as `to={to}&sender={from}&message={text}`, optionally the message id field and a read-only check address on the same host; the sender ID, clinic name, call-back number, rate and daily limit as before. Save, Test connection (only with a check address), then switch on with `ENABLE SMS`. Send the first one to a number the clinic owns and keep the daily limit low.
- **MM Lite:** in Meta Business Manager accept the Marketing Messages Lite terms for the WhatsApp Business Account (Meta's onboarding); then Settings, Integrations, Marketing messages through MM Lite: switch on with `SEND MARKETING THROUGH MM LITE`. Start with a small campaign and watch its statuses; switch off to go back to `/messages` at once.

## NOT verified

- **No real SMS gateway** was called. Whether a given UAE gateway accepts this request shape (flat JSON/form, `+` in the number, bearer/Basic), what it answers, and where its message id sits are for the administrator to check against the gateway's documentation and a number the clinic owns.
- **MM Lite against Meta**: the endpoint path `/{phone-number-id}/marketing_messages`, the request body being identical to `/messages`, the answer carrying `messages[0].id` (and `message_status: "accepted"`), statuses arriving on the `messages` webhook field with the same `wamid`, the pricing category value (`marketing_lite` assumed in the test), the error codes for a WABA that is not onboarded, and support for sending to a BSUID-only (username) contact all come from Meta's documentation as the author knows it and were **not** checked against an onboarded account. Meta has been renaming the product ("Marketing Messages API for WhatsApp"); check the current name, path and Graph version before switching on. Optional MM Lite request fields (such as `message_activity_sharing`) are not sent.
- **No browser**: the provider option, its fields and the MM Lite card were typechecked and built, not clicked.
- **Delivery receipts** for the generic gateway do not exist; the MM Lite "held for quality" or other new status values (if Meta sends them) are ignored by `fromWebhookStatus` like any unknown status.

## Suggested follow-ups

A `{to_digits}` placeholder and a custom auth header name for gateways that need them; a per-number MM Lite switch if only one WABA is onboarded; counting MM Lite sends separately in the campaign reports (the message row does not yet record which endpoint was used; the job logs it).
