# Phase 20e (channels and calendar) notes: website chat, Instagram and Messenger, Google Calendar busy sync

Closes the channel and calendar parts of `docs/21_SANOFLOW_PARITY_PROMPTS.md` section 20e: **G12** (website chat widget, Instagram, Messenger; generic SMS and MM Lite are NOT part of this phase) and **G7** (Google Calendar two-way busy sync per specialist). The reports part of 20e (G13) was built separately. Built in a cloud sandbox with plain Postgres 16 (pgvector, pgmq, cron/net stubs) and a PostgREST in front, no browser, no Supabase Auth or Storage stack, and **no real provider**: every Meta and Google call is a fake `fetch` returning responses written from the providers' documentation. `tests/setup.ts` now also makes any `fetch` to `instagram.com`, `facebook.com`, `messenger.com`, `googleapis.com` or `google.com` throw (Meta's Graph host was already blocked).

**All four are OFF by default** (`integration_accounts.enabled = false`) and each needs its typed words to switch on: `ENABLE WEBSITE CHAT`, `ENABLE INSTAGRAM MESSAGES`, `ENABLE MESSENGER MESSAGES`, `SYNC CALENDARS WITH GOOGLE`. The WhatsApp paths are unchanged except for one channel-type branch in the outbound handler and `type = 'whatsapp'` filters where a WhatsApp number is chosen (list below).

## What exists

| Item | Where | What it does |
|---|---|---|
| **Channel types** | migration `20261110000700`; `lib/channels/types.ts`, `ensure.ts` | `channels.type` accepts `web`, `instagram`, `messenger`. Such a channel has `waba_id = ''` and a namespaced `phone_number_id` (`web:<org id>`, `instagram:<IG account id>`, `messenger:<page id>`; a check constraint enforces it), so no WhatsApp lookup by phone number id or WABA can ever match it. The row is created on first use (`ensureChannel`). `replyWindow()` is the one rule for when staff may reply: WhatsApp unchanged (`serviceWindow`, templates outside), Instagram/Messenger 24 hours after the person's last message and nothing outside it, website chat always |
| **Website chat widget** (`web_chat`) | `public/widget/pulse-chat.js`, `app/api/widget/[key]/config` and `/messages`, `lib/channels/web/*`, settings card `web-chat-embed.tsx` | One `<script>` line (shown on the integration page) adds a chat button: vanilla JS, closed shadow root, text rendered with `textContent` only, no cookie, `credentials: "omit"`. Settings: allowed websites (host names, `*.example.com` for sub-domains, https only), title, colour, welcome text. The routes answer only while the integration is on, outside training workspaces and for an `Origin` on the list (CORS echoes that origin only; unknown/off/training all give the same 404). The **first message** creates a 256-bit visitor token (returned once, kept in the visitor's `localStorage`; only its SHA-256 is stored in `web_chat_sessions`), a contact with no phone (`source = 'web_chat'`, the optional name or "Website visitor") and an open conversation on the web channel. Replies are fetched by **polling** (`GET /messages`, Bearer token; every 5 s while the panel is open, 30 s otherwise): the visitor sees only their session's current conversation, only their own messages and the clinic's sent text replies, never notes, staff names or other conversations; fetched replies are marked `delivered`. Rate limits (`WIDGET_RATE_RULES`, counted in Postgres through `lib/rate-limit.ts`): sends 30/min per IP and 10/min per visitor, 10 new visitors per IP and hour, polls 240/min per IP and 30/min per visitor, refusals 30/min per IP; 8 KB body cap; 2,000-character messages |
| **Instagram and Messenger** (`instagram`, `messenger`) | `lib/integrations/meta-messaging/*`, `app/api/webhooks/integrations/{instagram,messenger}/[accountId]`, migration `…100` | Catalogue entries with Page ID (and Instagram account ID), Page access token, app secret and webhook verify token (all three credentials encrypted). **Inbound**: `GET` is Meta's handshake (echoes `hub.challenge` only when `hub.verify_token` equals the stored token, constant time); `POST` goes through `receiveIntegrationWebhook` with `X-Hub-Signature-256` (HMAC-SHA256 of the raw body with the stored app secret). Only person-to-business `message` events addressed to the configured Page / Instagram account are used (echoes, reads, reactions, postbacks, deletions are ignored); each is claimed once and stored by `channel_receive_social()`: the sender is matched by the **platform-scoped id on this channel** (`contact_channel_identities`, never `phone_e164`/`wa_bsuid`); a new sender becomes a contact without phone ("Instagram user" / "Messenger user"). | **Inbox** | `app/(app)/inbox/*` | The composer hides WhatsApp-only features on the new channels (number switch, templates, files, camera, voice notes, Media Library, flow shortcuts; a quick reply's file is dropped) and shows "text only" or the closed-window sentence. `sendChat` re-checks the window; `sendAttachment`, `sendLibraryMedia` and `sendTemplateMessage` refuse non-WhatsApp conversations; blue ticks are only sent for WhatsApp; "New conversation" and number switching list WhatsApp numbers only. The header shows "Website chat contact" / "Instagram contact" instead of "WhatsApp username user" |
| **Inbound side effects** | `lib/channels/inbound.ts` | After a message is stored: default-team / round-robin routing of a new conversation, the owner's notification or the escalation ladder, and the Phase 17 emergency-wording screen, as for WhatsApp. **No domain events** (`conversation.opened`, `message.received`, `contact.created`) are emitted for these channels, so no flow, recall listener or outbound webhook fires (the flow nodes send WhatsApp messages) |
| **Google Calendar busy sync** (`google_calendar`) | `lib/integrations/gcal/*`, migration `20261110000800`, `app/api/integrations/google-calendar/callback`, settings panel `gcal-panel.tsx`, actions `gcal-actions.ts`, task `gcal_sync` | OAuth per specialist (`integrations.calendar`): Connect stores a one-time state (SHA-256, 10 minutes, bound to the person, workspace and specialist) and sends the browser to Google (scope `calendar.events`, offline); the callback (signed-in, same person) exchanges the code once and stores the refresh and access tokens AES-256-GCM in `gcal_connections` (service-only). The `gcal_sync` task (pg_cron every 5 minutes, at most 20 due connections a run, at most 40 event writes per connection) **pulls** the calendar's events for yesterday to N days ahead (asking Google only for id, status, transparency, start, end and the private marker: never titles, descriptions, attendees or locations) into `time_blocks` rows with `source = 'google'` through `gcal_apply_busy_blocks()` (idempotent, keyed by a hash of the event id, only inside the window it read, never on an incomplete read); availability and `book_appointment` already honour time blocks, so Google busy time blocks bookings. It **pushes** the specialist's awaiting/confirmed/completed appointments as events built only by `buildBusyEvent()` (title "Busy", start, end, opaque, private, no reminders, a private marker; a deterministic event id so a lost answer never creates a second event), updates them when moved and deletes them when cancelled, no-show, reassigned or deleted (`gcal_event_links` keeps ids and a hash). Failures back off (5 minutes doubling, 6 hours max; 24 hours after a withdrawn grant). Disconnect deletes Pulse's future events (bounded), revokes the token at Google, wipes the tokens and removes the busy blocks; switching the integration off removes every mirrored block at once and the task makes no Google call for that workspace |
| **Read-only mirror** | trigger `time_blocks_mirror_guard` | A Google block cannot be inserted, changed or deleted by anything but the two sync functions (cascades from deleting the specialist or the organisation still work). Its reason is always "Busy (Google Calendar)" |
| **Erasure and merges** | triggers `contacts_erase_phase20e`, `contacts_move_channel_identities_on_merge` | Erasing a contact deletes their platform ids and widget sessions (the old browser token then finds nothing); a merge moves both to the surviving record |

## NOT verified

- **No real provider was ever called.** Meta's Messenger Platform for Messenger and Instagram (the webhook payload shape, the `object` values `page` / `instagram`, the Send API path `/{page id}/messages` with a Page token for both platforms, `messaging_type: RESPONSE`, the window error code 10 / subcode 2018278, code 551, the handshake parameters) and Google's OAuth and Calendar API (token responses, `invalid_grant`, `fields` filtering, client-chosen event ids and the 409 on a repeat, PUT restoring a cancelled event, 404/410 on delete) come from documentation as the author knows it. **Check each against a test Page, a test Instagram professional account and a test Google account before switching anything on.** Instagram in particular may need the newer "Instagram API with Instagram Login" (host `graph.instagram.com`, an Instagram user token) instead of the Page-token flow assumed here; that would be a new provider option on the same catalogue entry.
- **Meta app review.** Messaging permissions (`pages_messaging`, `instagram_manage_messages`) need Meta's app review and a business verification before they work for people outside the app's roles; health businesses may face extra review. Nothing in Pulse can check this.
- **No browser.** The widget script, the settings panels and the inbox changes were typechecked, linted and unit-tested, never clicked. The widget has not been tried on a real website, in Safari's storage partitioning, or with a strict Content-Security-Policy on the host site (the host page must allow the Pulse origin in `script-src` and `connect-src`).
- **Delivery and read receipts** for Instagram/Messenger are not processed: replies stay "sent". Website chat replies become "delivered" when the visitor's widget fetches them; there is no "read".
- **Profile names** are not fetched from Meta: senders appear as "Instagram user" / "Messenger user" until staff rename them.
- **pg_cron** for the three new schedules (the harness has a stub; `gcal_sync` is an `app.ping_jobs` call like the other tasks).
- **Types**: `lib/supabase/types.ts` was edited by hand in the generated format (five tables, two `time_blocks` columns, four functions); run the drift check on a real stack.
- **Load**: the widget poll is one indexed query per visitor every 5 seconds while open; unmeasured beyond clinic volumes. The busy sync reads at most 4 pages of 250 events per specialist; a calendar with more is left unchanged that run (the mirror is never replaced from a partial read).

## Decisions and deviations worth knowing

1. **Polling, not Realtime, for the widget.** A visitor has no Supabase session; Realtime would need a custom JWT per visitor and an RLS policy on messages for anonymous tokens. Polling an unguessable token through one narrow route is simpler and exposes nothing else. Cost: up to 5 seconds of delay.
2. **The visitor token is created by Pulse on the first message**, not by the browser, and only its hash is stored. Opening the widget without writing creates nothing in the database.
3. **Website chat needs typed words** (`contactsPatients: true`) even though no third party is involved: it creates patient records from the public internet. It is refused in training workspaces (same 404) so a demo cannot be reached by real visitors.
4. **No domain events for the new channels.** Flows, recall listeners and outbound webhooks stay WhatsApp-only in this phase; routing, notifications, escalation and the emergency screen do run. A later phase can emit events with a `channel_type` once the flow nodes know how to answer on these channels.
5. **Instagram and Messenger have no template fallback and no human-agent tag.** Outside 24 hours the reply is refused with a sentence; Meta's 7-day `HUMAN_AGENT` tag needs separate approval and was not used.
6. **One channel per Page / Instagram account and per workspace website chat**, created on first use. A Page cannot be connected to two workspaces (the channel reference is unique).
7. **Google busy blocks live in `time_blocks`** (with `source = 'google'`) so availability, the waiting list and `book_appointment` honour them without code changes; a trigger keeps them read-only. Unite appointments of the specialist are pushed to Google as "Busy" like any other (Unite itself is never written).
8. **Connecting a doctor needs `integrations.calendar`** (Manager preset), and the same person must finish in the browser: in practice the doctor signs in to Google on the manager's screen, or the doctor is given the permission. A doctor-self-service button is a follow-up.
9. **Disconnect deletes only future events** Pulse wrote (at most 200, best effort); past "Busy" entries stay in the doctor's calendar as history.
10. **The widget script has no Subresource Integrity hash** in the embed line: it is served by Pulse itself and changes with releases. Bump `WIDGET_VERSION` in the script when it changes.

## Integration review fixes (merged branch)

- **Widget polling looks back 2 minutes** (`POLL_OVERLAP_MS`): a reply queued before the visitor's last message and sent after it is still shown (the widget skips ids it already has).
- **Instagram / Messenger sends are claimed atomically** (`queued` to `sending`). A message found already `sending` was handed to Meta by a worker that died before recording the answer: it is marked failed as possibly delivered and never posted again.
- **Flows never start on these conversations**: `startRun` refuses a conversation whose channel is not WhatsApp (`channel_not_supported`), which also covers staff actions that emit `conversation.closed` / `conversation.waiting` and the shortcut button.
- **Routing and team auto-reply** use the Phase 20c router (`routeConversation`, `sendTeamAutoReply`), as for WhatsApp.
- **Close-with-enquiry** sets the enquiry source from the channel (`website`, `instagram`, `messenger`).
- **Google busy blocks** cannot be removed from the calendar view (the action says so instead of reporting success). **Reconnecting** a doctor's calendar first runs the disconnect clean-up (future events deleted, grant revoked, busy blocks cleared); the new connection's first sync brings the busy times back.
- **Widget POST** answers 503 with its CORS headers when something unexpected fails.

## How an administrator switches each on

- **Website chat**: Settings, Integrations, Website chat: list the websites, set title, colour and welcome text, Save, switch on with `ENABLE WEBSITE CHAT`, then paste the line shown under "Add the chat to your website" before `</body>` on those websites.
- **Instagram / Messenger**: create the Meta app, connect the Page (and the Instagram professional account), get a long-lived Page token with the messaging permissions (after Meta's app review); enter Page ID (and Instagram account ID), Page token, app secret and a verify token of your choice, Save, Test connection, switch on with `ENABLE INSTAGRAM MESSAGES` / `ENABLE MESSENGER MESSAGES`, then in the Meta app's Webhooks settings subscribe the `page` / `instagram` object's `messages` field with the address shown on the page and the same verify token.
- **Google Calendar**: in Google Cloud create an OAuth client (web application), enable the Calendar API, add the redirect address shown on the page; enter client ID and secret, choose pull/push and the number of days, Save, switch on with `SYNC CALENDARS WITH GOOGLE`, then press Connect for each doctor (the doctor signs in to their own Google account).
