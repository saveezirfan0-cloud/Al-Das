# Phase 20f (inbox extras) notes: forward, contact card, catalogue product, employee call, move chat to a new contact

Closes Sanoflow parity gap **G11** (`docs/20_SANOFLOW_REA_PARITY.md` §4): forward a message, share a contact card, send catalogue products, click-to-call, and unlink a chat from a contact. Built lean on top of the existing inbox: **no new table, no new permission, no new environment variable, one SQL function**. Every send goes through `queueOutbound` (`lib/inbox/send.ts`), so the outbound job still applies training mode, the 24-hour window, the per-number rate limit and the stop rules exactly as for a typed reply. Built in a cloud sandbox (plain Postgres 16 + PostgREST, no browser, no Meta).

Templates, interactive messages, locations, contact cards, reactions, notes and system rows are refused. A file that has not finished downloading is refused. | **Employee call** | `telHref` (`lib/inbox/extras.ts`); Call button in the conversation header | A plain `tel:+<E.164>` link that the staff member's own phone or softphone dials. | **Move chat to a new contact** ("unlink") | `unlinkConversationContact`; SQL `public.unlink_conversation_contact` (migration `20261112000100`); `UnlinkDialog`; "Move chat to a new contact" in the sidebar's More tab | See the decision below. One transaction: a new contact (typed name, `source = 'inbox'`) takes over the WhatsApp identity (`phone_e164`, `wa_bsuid`, `wa_profile_name`) plus `language` and the opt-outs (`stop_marketing`, `sms_opt_out_at`, `no_review_requests_at`; `promotions_opt_in` is NOT copied); this chat and the old contact's other **live** WhatsApp chats move to it; the old contact keeps its record, Unite PIN, appointments, enquiries, closed chats and non-WhatsApp chats; an alternate-phone row with the moved number is removed (it would keep matching inbound messages to the old record). `unlink_conversation_contact` is `security definer`, `search_path = ''`, revoked from `public`, `anon`, `authenticated`, granted to `service_role` only; the action calls it with `createAdminClient(member.userId)` after the checks. Database refusals with fixed wording are mapped to plain sentences; anything else is logged through `redactText` (code only) and shown as "Could not move the chat. Nothing was changed."

## Decisions

1. **Forward and the window.** No template fallback: outside the target's reply window the action refuses with a sentence (`extrasWindowClosedMessage`) and the picker hides closed conversations. The outbound job re-checks the window (131047) anyway.
2. **Forward to a non-WhatsApp conversation:** text only, through the existing Phase 20e path (`queueOutbound` → `deliverChannelOutbound`, which already refuses non-text and Instagram/Messenger outside 24 hours). Files to those channels are refused before queueing. Contact cards and products are WhatsApp only.
3. **Forwarded files are copied, not re-referenced:** the target conversation gets its own stored copy, so the strict media path check (`isMediaPathFor`) and deleting/erasing either conversation keep working. The source path must sit in the source conversation's own folder or the forward is refused. Meta's forwarded label is not available in the Cloud API, so the patient sees a normal message.
4. **"Unlink" means the WhatsApp identity moves.** A WhatsApp chat belongs to the number; the only consistent way to file it under a different person is for that person to hold the number (outbound needs a phone or BSUID on the conversation's contact, inbound matches by BSUID then phone then alternate phones). Moving a chat to a phone-less contact would make every reply fail. Live WhatsApp chats on other numbers move too, because their replies go to the same number; closed chats stay as the old contact's history (reopening one and replying fails with "The contact has no WhatsApp phone or user id"; start a new chat from the new contact instead).
5. **Household links block the move.** If the old contact is already a guardian or a dependant, the move is refused ("remove the family links first") instead of guessing how to re-shape the household (one level deep, `household_no_chain`).
6. **Only a chat on the contact's MAIN identity can move** (review fix). The new contact takes over the old contact's main phone and BSUID, so the person writing must be on that identity: the sender (Meta's raw `from`) of the chat's latest inbound message must equal the main phone (digits) or the BSUID. A chat that came in on one of the contact's alternate numbers (`contact_phones`, matched by `lib/inbox/contacts.ts`) is refused ("edit the contact's numbers instead"), and so is a chat nobody has written in yet. Checked in the action (`checkChatSender`, `lib/inbox/unlink.ts`) for a clear sentence and again inside the SQL function under the row locks. The function locks the contact first and then the conversation (same order as `merge_contacts`).
7. **The moved messages follow the new contact for privacy purposes.** Because messages belong to their conversation, after a move the chats' messages are no longer part of the old patient's data export or erasure (`erase_contact`) and are exported/erased with the new contact instead. That is correct only when the chat really is the other person's: **staff should move a chat only when it genuinely belongs to someone else**, never to tidy up or to separate one patient's own messages. The audit row (`conversation.contact_unlinked`, old and new contact ids, moved conversation ids) and both timelines record every move so a privacy request can follow it.
8. **Sends are queued before the bot is stopped** (review fix): every extra calls `takeOverFromBot` only after `queueOutbound` succeeded, and a forwarded file copy is removed again if queueing fails. Contact-card first and last names are capped at 100 characters each so the send schema always accepts the card.
9. **Contact cards are typed, not picked** from contacts, so the feature cannot send one patient's number to another.
10. **Lean UI:** the four dialogs live in `extras-dialogs.tsx` and load through `next/dynamic` only when opened; the composer gained two icon buttons (contact card always on WhatsApp, product only with a catalogue), the header a Call button, each message a "forward" button next to "reply" (44 px on touch screens, shown in a row under the message there), the sidebar's More tab one button.

## NOT verified

- **No real Meta call.** The `contacts` message and the interactive `product` / `product_list` bodies follow Meta's Cloud API documentation as the author knows it (single product: no header; product list: header and body required, sections with titles, max 30 items). Products also need the catalogue to be connected to the WhatsApp Business Account and the products approved in Commerce Manager; Meta's errors for a missing catalogue or product come back through the normal error map. Try both on a test number first.
- **No browser.** The dialogs, buttons and touch layout were typechecked, linted and built, never clicked or screen-read.
- **Unite patient sync** fills blank phones on contacts it matches by PIN: after a move, the old contact (which keeps the PIN) has no phone, so a later sync may try to give the number back; the unique index refuses it and `fillBlanks` ignores the failure (no data changes). Not exercised against Unite.
- **Inbound matching after a move** was checked at the data level (one contact holds the phone and BSUID, the alternate row is gone), not by replaying a webhook.
- Types in `lib/supabase/types.ts` were edited by hand for the new function; run the drift check on a real stack.
