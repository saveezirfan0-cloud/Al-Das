# Finance access window: notes

Closes the `docs/09` §2.3 Security gap "working-hours or IP restriction for finance". Built in a cloud sandbox with plain Postgres; type-checked, linted and tested, not driven in a browser or behind Vercel.

Migration `supabase/migrations/20261125000100_finance_access_window.sql`; paste file `deploy/supabase-paste/65_finance_access_window.sql` (same SQL). The setting itself is `orgs.settings->'finance_access'` (no new table). The migration adds the alert kind `finance_access_denied`, write-time validation (`app.finance_access_problem` behind the trigger `orgs_finance_access_guard`), the read path (`app.finance_window_hours`, `app.finance_window_reason`, `app.finance_window_open`), and redefines `app.has_perm`, `app.has_perm_wild` and the accounting ledger's five read helpers (`app.acc_can_view`, `acc_can_read_journals`, `acc_can_read_receivables`, `acc_can_read_banking`, `acc_can_read_budgets`) so the database follows the days and hours too, ledger included.

**What applies where.** The **days and hours** apply everywhere: Pulse's pages, actions and API routes, and any direct use of the database with a member's token (Supabase REST, Realtime), through row level security. The **address list** applies to Pulse's own pages, actions and API routes only: the database cannot see the person's address (server reads arrive from Vercel), so a member calling the Supabase API directly from an unlisted network inside the hours is not stopped by the list. The Settings screen says so.

## What exists

| Part | Where | What it does |
|---|---|---|
| Setting | `lib/security/finance-access.ts` (`financeAccessSchema`, `readFinanceAccess`, `writeFinanceAccess`) | `enabled` (default **false**), `limit_hours`, `days` (ISO 1 = Monday ... 7 = Sunday, default Monday to Saturday), `start` / `end` (HH:MM in the org timezone, `orgs.timezone`; default 07:00 to 21:00), `ip_allowlist` (IPv4/IPv6 addresses and CIDR ranges, max 50, stored canonical with host bits cleared, `/0` refused), `scope` (`finance_roles` = every role holding any `finance.*` / `accounting.*` key, or `selected_roles` with `role_ids`). The completeness rules (a day, a role, hours or addresses) apply only while `enabled`, so a switched-off draft can be saved half-filled |
| Decision (app) | `financeAccessDecision({ now, timezone, stored, ip, member })` (pure) | Order: Admin (`*`) allowed; a role without finance/accounting keys allowed; a stored value that plainly says `enabled: false` is off even if the rest does not validate; any other unreadable value **denied** (`invalid_settings`); switched off allowed; role not in scope allowed; address list set and no address **denied** (`ip_unknown`) or not on it **denied** (`ip_not_allowed`); days/hours checked (`day_not_allowed`, `outside_hours`; an invalid timezone denies). Start is inclusive, end exclusive; start > end is an overnight window that belongs to the day it opens; start = end is the whole day |
| Validation (database, write time) | `app.finance_access_problem(cfg, tz)`, trigger `orgs_finance_access_guard` (BEFORE INSERT/UPDATE OF settings, timezone on `orgs`) | Checks the stored value once, when it changes: shape, days, HH:MM, addresses (Postgres `inet` syntax, a little looser than the app's parser; `/0` refused), scope, role ids, and the completeness rules while on. While the window is on, `orgs.timezone` must be a name in `pg_timezone_names` (offsets such as `+04:00` or `UTC+4` are refused: Postgres reads them POSIX-style, sign reversed; the app refuses them too, `isNamedTimeZone`). A refused write raises 23514; the Settings action checks the timezone first and says so. Unrelated updates of an organisation are not checked |
| Decision (database, read time) | `app.finance_window_hours(cfg, tz, role_id, now)`, `app.finance_window_reason(...)` (adds Admin and "nothing to restrict"), `app.finance_window_open(org)` (STABLE, SECURITY DEFINER, `search_path = ''`) | The same rule and reason words as the app, without the address list. A cheap structural read of the already-validated value: no exception blocks, no address loop (about 8 to 12 µs a call measured on plain Postgres 16, 50 addresses included). Missing or ill-typed fields of a switched-on value (one written before the check) still give `invalid_settings`, i.e. closed. `finance_window_open` reads `orgs.settings` and `orgs.timezone`, returns true at once when nothing is stored or `enabled` is `false` or missing, otherwise reads the caller's role (`auth.uid()` in that org); Admin `*` passes |

## Decisions

1. **Admin is never restricted**, in the app and in SQL, whatever is stored, so nobody can lock the clinic out of fixing it. Admin roles cannot be ticked in "Only these roles".
2. **Fail closed where it matters.** A stored value that does not validate (only possible by editing the database) closes finance for every finance role until an Admin saves it again, in the app and in the database, unless it plainly says `enabled: false`. A missing, unparseable or untrusted (not on Vercel) client address is refused only when an address list is set.
3. **Hours in the database, addresses in the app.** Postgres sees the time but not the person's address, so the database enforces days and hours only (for every finance and accounting table, the ledger included). This is stated in the Settings form, this note and `docs/09`.
4. **No middleware query.** The window is decided in `getCurrentMember()` from the org row it already loads; the middleware only forwards the path header. In SQL the off path is one `orgs` read, and only for finance or accounting keys.
5. **Only finance and accounting keys are taken away.** A receptionist who holds `finance.cashup` loses cash-ups outside the window and keeps the inbox, appointments and everything else.
6. **Address privacy.** The alert keeps the network and a keyed hash; the full address is shown only to the person themselves on the refusal page and to the person saving the settings (their own address).
7. **Jobs and service-role code are unaffected:** they do not go through `getCurrentMember()` or `auth.uid()`.
8. **Validate once, read cheaply.** The full check runs when the setting or the timezone is written; every RLS check only reads the fields. A value that somehow skipped the check still fails closed when ill-typed.

## Known limits

- The address list does not stop direct database access with a member's token from an unlisted network inside the hours (see above). Row level security still applies the role's permissions and the hours.
- The app decides with the server clock and the database with `now()` (transaction start); at the exact closing minute a page may be allowed and its data refused, or the reverse, for a moment.
- `app.finance_window_open` runs for each row a finance or accounting policy checks (like `has_perm` itself). With the window off that is one primary-key read of `orgs`; with it on, an `orgs` read, a membership read and the cheap rule, a few tens of microseconds per check.
- While the window is on, the organisation's timezone cannot be changed to an offset or an unknown name (the database refuses the update).
- Outside the window Finance and Accounting disappear from the menu for the covered roles; typing a finance address shows the explanation page.
- Someone already on a finance page when the window closes sees their next action refused with the normal "not allowed" message; the next navigation shows the explanation page.
- Not exercised against a real Vercel deployment or Supabase project.

## Tests

- `tests/unit/finance/fixtures/finance-access-window.synthetic.json`: shared parity cases (nothing stored, switched off, off-but-malformed, malformed while on, Admin, scope, hour boundaries, closed days, DST in Europe/London both ways, overnight and whole-day windows, invalid timezone, address-only windows). Both `tests/unit/security-finance-access.test.ts` (app) and `tests/db/finance-access-window.test.ts` (SQL) must give each case's `expect`.
- `tests/unit/security-client-ip.test.ts`: header order, trust only on Vercel, garbage headers, IPv4/IPv6 parsing, canonical ranges, CIDR boundaries v4/v6, cross-version, network labels.
- `tests/unit/security-finance-access.test.ts`: schema defaults and validation (completeness only while on), read/write keeps other settings, off-before-validation, reason classes, `can()` with restricted areas, plus the parity cases.
- `tests/unit/security-finance-access-session.test.ts`: the session wiring (off changes nothing, refused member loses finance/accounting only, refusal recorded after the response on finance and API paths and not on others or for prefetches, untrusted headers off Vercel, Admin bypass, page redirect vs action `ForbiddenError`).
- `tests/unit/security-finance-access-server.test.ts`: alert contents (no full address), dedupe key per reason class and day, never throws.
- `tests/unit/security-middleware-mfa.test.ts`: the path header is forwarded and overwrites a browser value.
- `tests/db/finance-access-window.test.ts`: the alert kind; SQL parity with the fixtures (a case the database refuses to store is compared by that refusal); every app-invalid case is refused at write time; the read path fails closed on ill-typed values; `has_perm` / `has_perm_wild` refuse finance and accounting keys outside the hours and keep other keys, Admin and the window-off case unchanged; RLS reads and writes of `fin_ref_denial_codes` and reads of `acc_cost_centres` follow the window (Admin still reads); the five ledger helpers say no outside the hours; the trigger refuses invalid values and offset timezones and leaves unrelated updates alone; the guard on functions that read `roles.permissions`.
