# Phase 20i notes: Meta ads spend metrics (parity gap G13, last part)

Spec: `docs/20_SANOFLOW_REA_PARITY.md` §4 row G13 ("Meta ads spend metrics are not built"), on the Phase 19 integration foundation (`docs/18_PHASE_19A_NOTES.md`, "How to add the next integration") and next to the Phase 19b ad attribution (`docs/19_PHASE_19B_NOTES.md`). Built in a cloud sandbox with plain Postgres 16 and PostgREST, **no Meta account of any kind**: the adapter was only ever driven by fake `fetch` functions answering with responses written from Meta's documentation.

**OFF by default** (`integration_accounts.enabled = false` for kind `meta_ads`). It is a pull only: Pulse reads Meta's own per-ad totals and sends Meta nothing about patients.

## How an administrator switches it on

1. In Meta Business Settings create (or reuse) a **system user**, give it the ad account with the **ads_read** permission only, and generate a token for the app with `ads_read`.
2. Settings, Integrations, **Meta ads spend**: enter the ad account ID and the token, keep 7 days (or choose up to 28), Save, then **Test connection** (it reads the account's id and currency, nothing else).
3. Switch it on (no typed words: it only reads). The first pull runs at the next 04:17 UTC; to see data at once, run the task by hand (`pnpm jobs:run ads_insights_sync` against that environment).
4. Open Reports, **Ad attribution**: spend and cost columns appear. Cost per result needs Meta ad attribution (Phase 19b) on as well, since the conversations come from it.

## Decisions

1. **One integration of its own** (`meta_ads`), not more fields on `meta_capi`: different credentials (ad account and `ads_read`, not a dataset), no data shared, no typed words, and it can be on while ad attribution stays in report-only mode or off.
2. **Replace the range, not just upsert.** Meta restates recent days and stops reporting an ad-day that had nothing; replacing the pulled range keeps the table equal to Meta's latest answer. Days outside the range are never touched.
3. **Complete days only** (ending yesterday, UTC dates). Meta's days are in the ad account's time zone; the report states that. A clinic in Dubai with a Dubai ad account sees whole local days.
4. **Fail closed on a bad pull.** One unreadable row means the whole pull is dropped and the previous figures stay; the reason shows on the integration page and System health.
5. **Money as integers** (thousandths) in the database and in every calculation; formatted only for display. The report divides like by like: totals per currency use only the ads that have spend in that currency.
6. **No retention job**: the rows are Meta's aggregates per ad, with no patient data. Switching the integration off stops pulling and hides the spend columns; stored rows remain (they are deleted with the organisation).
7. **No new permission**: the report stays `ads.view`, settings `integrations.manage`.

## NOT verified

- **No Meta account was ever called.** The insights endpoint, `time_increment=1` with `time_range`, the field names (in particular `account_currency` on an insights row), the bearer header for the Marketing API, the error codes (190, 200, 80000 range), paging by `after`, and the ad account read used by Test connection all come from documentation as the author knows it. **Check against a real ad account (read only, harmless) before relying on the numbers.**
- Whether the ad id in WhatsApp's `referral.source_id` always equals the insights `ad_id` for click-to-WhatsApp ads (both are documented as the ad id; unconfirmed on live data).
- Meta's attribution of spend to days in the ad account's time zone versus Pulse's report window (UTC instants): the two periods can differ by a few hours at each end.
- pg_cron in the real stack (the harness stubs it; the schedule row was checked).
- No browser: the report and the settings page were typechecked and built, not clicked.
