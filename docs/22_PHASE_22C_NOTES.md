# Phase 22C notes: digital signatures on approval certificates and close packs

_Built 13 Oct 2026 on the 22C worktree branch (based on `claude/funny-clarke-6t7gee` at `edb63eb`). Plan: `docs/22_ACCOUNTING_PLAN.md` §2 (last row) and §6 (22C); `docs/20_FINANCE_CONTROL_PLAN.md` §1.1 (the CEO's zero-paper directive: maker, checker, approver, "digital signature certificates (DSC) for the CEO and Finance Manager") and §4 point 4; open questions OQ-91 and OQ-121._

## Why this design

The directive asks for DSC-signed approvals. A DSC in the UAE (and in Tally) is a USB token: the private key never leaves the token and is driven by a desktop driver on the signer's own computer. A web application cannot reach it (browsers removed the old `crypto.signText` / Java applet routes long ago), so Pulse cannot "sign with the DSC". What Pulse can do, with no external service:

1. **Organisation seal (PAdES).** The final approval certificate PDF of a payment voucher and the PDF of a locked month-end close pack carry a real PDF digital signature (SubFilter `ETSI.CAdES.detached`, ByteRange over the whole file, detached CMS with SHA-256 and RSA, ESS signing-certificate-v2, signing time in `/M`: PAdES baseline B-B). Any validator (Adobe Acrobat / Reader, poppler `pdfsig`, the EU DSS demo) shows "signed by <organisation seal>, document not modified since signing".
2. **Personal signatures (CMS over an approval statement).** Where a signer has a *soft* certificate (.p12 / .pfx), they upload it once and type its PIN at their approval step (voucher verify, department approval, CEO authorisation; Finance and CEO close sign-offs). Pulse signs a canonical approval statement and stores the detached CMS with the step, in the same transaction. The certificate PDF lists each signature (subject, issuer, serial, fingerprint, validity, verification result) and is then sealed.

Alternatives considered and not taken:

- **Personal PAdES signatures inside the PDF** (one incremental signature per approver). The certificate PDF is rendered after the last approval; earlier approvers would have to sign a document that does not exist yet, or every approval would need a new incremental revision of a stored PDF. Signing a statement bound to the content hash the step is already bound to (20D) is simpler, keeps one rendering path, and proves the same thing (this person approved exactly this content).
- **Regenerating the sealed PDF deterministically** on every download. Possible (pdf-lib output and RSA PKCS#1 v1.5 are deterministic given the signing time), but a renewed seal certificate, a later trail event (payment, Tally export) or a library upgrade would silently change the bytes and an auditor's copy would no longer match. **Chosen: store the sealed PDF** in `fin_sealed_documents` (bytea, one row per document and bound hash, first writer wins, append-only). It is small (about 20 to 60 KB), testable on plain Postgres, atomic with its unique key, and leaves no orphan files. The `finance-documents` bucket was the other option; a row avoids the storage round trip and the orphan-file cleanup.
- **@signpdf/signer-p12** (node-forge PKCS#7). It adds a CMS signing-time attribute (PAdES baseline forbids it), has no signing-certificate-v2 attribute, and node-forge cannot verify PKCS#7 at all. Pulse builds and verifies the CMS itself (`lib/signing/cms.ts`, `verify.ts`, ~300 lines over a small DER reader/writer), and uses node:crypto for the RSA operations.

## Tables (migration 20261108000200)

- `fin_signing_certificates` (service-only; RLS on, no policy): org, user, the .p12 as base64 encrypted with `lib/crypto.ts` (AES-256-GCM, `ENCRYPTION_KEY`), subject / CN, issuer / CN, serial, sha256 fingerprint, validity, created, revoked. One active certificate per person and org (partial unique index). A row is never deleted and can only be revoked, which also drops the encrypted file (`p12_enc` null; check constraint and trigger). The PIN is never stored: it is typed at upload (to read the certificate and refuse an expired or non-signing one) and at each signing.
- `fin_approval_signatures` (append-only, select policy only): org, document kind (`payment_voucher`, `close_pack`), document id, step (`check`, `approve_dept`, `approve_ceo`, `finance`, `ceo`), user, certificate id, the canonical statement and its sha256, the bound hash, the CMS (bytea), a copy of the certificate details, `step_at` (the transaction time of the step). **The select policy delegates to the document's own policy** (`exists (select 1 from fin_payment_vouchers ...)` / `fin_period_closes`, evaluated under the reader's row level security), so a department head sees only the signatures of vouchers they may read, special categories stay hidden, and close signatures follow the close permissions.
- `fin_sealed_documents` (service-only, append-only): org, kind (`voucher_certificate`, `close_pack`), document id, the bound hash (approved content sha256 / close snapshot sha256), the sealed PDF, its sha256 (generated column), seal subject and fingerprint, who triggered it. Unique per (org, kind, document, bound hash).
- `app.fin_store_approval_signature` (internal) checks the statement against the step it accompanies (type and version, document, org, step, signer, bound hash, remarks hash), freshness (10 minutes), CMS size, and that the certificate is the signer's own active one in this org with the same fingerprint and valid now; then stores it. SQL cannot check RSA, so the server verifies the CMS before calling (and the pages verify it again on every view).
- `public.fin_voucher_act_signed(...)` = `fin_voucher_act` + the signature, one transaction (verify / department / CEO only). `public.fin_close_sign_signed(...)` = `fin_close_sign_finance` or `_ceo` + the signature. Service role only.

## The rules

- **The approval statement** is canonical JSON with fixed keys: `type` (`pulse.approval-statement`), `v`, `doc_type`, `doc_id`, `doc_ref` (voucher number or close month), `org_id`, `step`, `signer_id`, `bound_sha256` (the content hash the step is bound to: the voucher's approved content hash, or the close snapshot hash), `remarks_sha256` (sha256 of the trimmed remarks or note, null when blank; the remarks themselves never go into the statement), `signed_at` (whole seconds). The CMS carries the signing time and signing-certificate-v2.
- **A wrong PIN never consumes the approval.** The server action opens the certificate with the PIN, checks it can sign now, signs and verifies its own signature *before* it calls the step. Any failure returns a clean error ("The certificate PIN is not correct. Nothing was saved.") and no step RPC runs. If the database then refuses the signature (stale, revoked, mismatch), the whole transaction rolls back, step included. Every attempt with a PIN counts against `signingPinPerUser` (10 per 15 minutes per person, fail closed); uploads against `signingCertUploadPerUser`.
- **Which signatures are current.** A signature counts for a step only when it was stored in the same transaction as the step (`step_at` equals `checked_at`, `dept_approved_at`, `ceo_approved_at`, `finance_signed_at` or `ceo_signed_at`), by the person who holds the step now, over the document's current hash. A rejected and resubmitted voucher or a withdrawn finance sign-off never shows an old signature as current; the old rows stay as history.
- **When the seal is applied.** A voucher's certificate is sealed when the voucher is approved in Pulse (`route = 'pulse'`, status approved or paid): right after the final approval step (best effort) and otherwise on the first download. A Tally-route voucher is not sealed (it is authorised in Tally). A close pack PDF is sealed when the month is locked: right after the CEO sign-off (best effort) and otherwise on the first PDF download. The Excel pack is not signed.
- **Same bytes every time.** The sealed PDF is stored per document and bound hash; every later download returns it, so the signature stays valid and the file identical even after the seal certificate is renewed. The sealed certificate is the document as at sealing time (normally the moment of final approval); a later payment or Tally export is on the voucher page, the trail and the Tally file, not in the sealed PDF. If a voucher is edited after approval (it returns to draft) and approved again, the new approval has a new content hash and gets its own sealed certificate.
- **Seal off or unusable.** No organisation seal (off, incomplete, expired, wrong password, no signing key usage) means the PDF is produced as before with a visible line "Not digitally sealed (no organisation certificate configured)." A broken certificate on a switched-on seal sets the integration's status to an error ("certificate unusable; documents are not sealed"). Non-final documents say why they are not sealed yet.
- **Switching the seal on** needs `integrations.manage` (Admin only), the typed words `SEAL DOCUMENTS` (new catalogue flag `signsDocuments`, counted by `needsConfirmation`), and no readiness problems: the stored .p12 must open with the stored password and its certificate must be valid now, RSA ≥ 2048, and allowed to sign (key usage digitalSignature or nonRepudiation when the extension is present). A file that cannot be opened with the password is refused when the settings are saved. The settings page shows subject, issuer, serial, validity, fingerprint and how many documents were sealed; never the file or the password.
- **Who holds a personal certificate.** Anyone with `finance.vouchers.check`, `finance.vouchers.approve_dept`, `finance.vouchers.approve_ceo`, `finance.close.signoff.finance` or `finance.close.signoff.ceo` sees Settings, Signing certificate and manages their OWN certificate only. Nobody else, administrators included, can sign with it (the PIN is theirs). Upload and revocation are audited with the fingerprint only. A PIN shorter than 4 characters, an expired or not-yet-valid certificate, a non-RSA key or a certificate without signing key usage is refused at upload.
- **Verification on the pages.** The voucher drawer (once submitted) and the close Sign-off card show "Organisation seal: Signature valid / Signature invalid / Not signed" (the stored sealed PDF verified on every page load) and each personal signature as "Signature valid / invalid" with the certificate name and issuer. Validity means: mathematically valid over these bytes, made by this certificate, inside its validity period. Pulse does not check revocation (CRL / OCSP) or chain trust to a root; that needs network calls. The settings page warns that a self-signed seal will be shown as "signer not trusted" by PDF readers.
- **Nothing is logged** except redacted error text without the PIN, key, file or statement remarks; audit diffs hold `signed: true/false` and the certificate fingerprint.

## Legal note (not legal advice)

The UAE framework (Federal Decree-Law No. 46 of 2021 on Electronic Transactions and Trust Services, and the TDRA trust-services rules under it) distinguishes ordinary electronic signatures, trusted electronic signatures and **qualified** electronic signatures; only a qualified signature (made with a qualified certificate issued by an accredited UAE trust service provider, on a qualified signature-creation device) has the presumptions of a handwritten signature. What 22C produces is **not** qualified:

- the organisation seal is an advanced-style electronic seal with whatever certificate the organisation supplies (often a commercial or self-signed one), held by the server;
- personal signatures use soft certificates whose key is stored (encrypted) on the server and unlocked by the PIN, which is not a qualified signature-creation device.

Together with the recorded approvals (maker / checker / approver in SQL, content hash, append-only trail, audit log) this is strong evidence for internal control and the auditors. Where a qualified signature is required, the routes are:

- **UAE PASS digital signature** (TDRA / Digital Dubai): the signer approves in the UAE PASS app on their phone; the relying organisation must be onboarded (agreement with Digital Dubai / TDRA, a sandbox then production integration, client credentials). Pulse would send the PDF hash, the signer would confirm in UAE PASS, and Pulse would embed the returned signature as an incremental PAdES signature. It needs network calls, an onboarding process that is not self-service, and per-signer UAE PASS accounts at the verified level. This would be its own slice (an integration in the catalogue, `sharesData`: the document hash and the signer's identity go to UAE PASS).
- **An accredited trust service provider's remote signing service** (cloud HSM, qualified certificates per person): the same shape through its API.
- **Keep using the DSC in Tally** (Ctrl+E) or the Phase 19b e-signature provider for the documents that legally need it (OQ-91).

**Timestamps.** There is no RFC 3161 timestamp (PAdES B-T) because a TSA is a network service and tests must not reach the network. The signing time is the server clock (`/M` and the CMS signing time), which the trail and the audit log corroborate. Adding a TSA later means one extra unsigned attribute in `cms.ts` and an integration entry; long-term validation (B-LT / B-LTA) would also need the CRL / OCSP responses embedded.

## OQ-121 (personal certificates)

Built so both answers work. If the CEO and the Finance Manager have, or obtain, soft certificates (.p12 / .pfx), they add them under Settings, Signing certificate and sign at their step. If they only have USB tokens, nothing changes for them: Pulse records the approval and seals the certificate with the organisation certificate, and the token stays in Tally. OQ-91 is answered for the organisation seal; the owner's decision on personal signatures (soft certificate, UAE PASS onboarding, or seal only) is still open.

## Not verified

- **Not opened in Adobe Acrobat** or the EU DSS validator (no GUI here); poppler `pdfsig` and OpenSSL accept the output, and the structure follows the PAdES baseline profile.
- **No real CA-issued or UAE certificate** has been used; only generated RSA test certificates. ECDSA certificates are refused (`unsupported_key`) because node-forge cannot read EC keys from .p12 files reliably; if the clinic's certificate is ECDSA, this needs a follow-up (node:crypto can sign with it; the PKCS#12 decoding is the gap).
- **Not clicked through in a browser** (no Supabase auth stack here): the file upload in the integration form, the PIN fields and the status badges have been typechecked, linted and built only.
- Revocation status and chain trust of certificates are not checked (no network).
