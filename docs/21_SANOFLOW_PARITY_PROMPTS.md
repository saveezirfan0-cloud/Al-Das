# Sanoflow parity: prompts for Claude Code

Companion to `docs/20_SANOFLOW_REA_PARITY.md`. Same method as `docs/10`: **one fresh Claude Code session per phase, Shift+Tab for Plan Mode, paste the prompt, review the plan, then let it build.** All `CLAUDE.md` rules apply.

## Paste this at the start of every session

> "Read CLAUDE.md, docs/09_STATUS_AND_ROADMAP.md, docs/20_SANOFLOW_REA_PARITY.md and the phase notes for the area you will touch. `docs/audit/sanoflow-surface.json` (endpoints, params, form fields, flow vocabulary) and `docs/audit/sanoflow-rea-shapes.json` (response field paths and types) are the captured Sanoflow contract: use it to decide behaviour, never to copy names, copy text or code (rule 14). Before planning, confirm each gap you are closing against the current code and tell me if any is already built. Work in Plan Mode: show the plan, files, migrations, tests and questions. No test may reach Meta, Unite, Anthropic, Stripe, Twilio or Google. When done run `pnpm typecheck && pnpm lint && pnpm test` (and `pnpm test:db` if SQL changed), update docs/20 §4 for the rows you closed, and write `docs/NN_PHASE_20X_NOTES.md` (what exists, how verified, what was NOT verified, open questions)."

## 20a: Sanoflow migration completeness (G1) · P0

> "Extend the Sanoflow import from contacts-only to everything the clinic needs on cut-over day. Use `docs/audit/sanoflow-rea-shapes.json` (field paths and types only) and its response shapes to confirm every field the mappers must handle and list any Sanoflow field Pulse has no column for. Sanoflow exports CSV for contacts, appointments (all), enquiries per pipeline and all, enquiry activity, and campaign reports (see `endpoints` in `docs/audit/sanoflow-surface.json`, modules `Appointments`, `enquiry`, `Patients`, `Campaigns`). Add importers under `scripts/import/` sharing `scripts/import/common.ts`: (1) pipelines, stages, statuses, lost reasons and enquiry custom fields (config, from a JSON file I will fill by hand from Settings, Enquiries); (2) labels, tags, quick replies, conversation categories; (3) enquiries with stage, status, value, source, UTM, assignee by e-mail, linked to contacts through `external_refs`; (4) enquiry activity as history entries; (5) future appointments only (past ones come from Unite), matched to specialist, service and location by name through a mapping file, booked through `book_appointment` so the advisory lock and capacity rules apply, never sending notifications; (6) static segments as membership lists, and dynamic segments translated from their stored filter JSON (shape in sanoflow-rea-shapes.json) into the Pulse filter AST, with anything untranslatable listed for manual rebuild; (7) roles, mapping the view/manage/delete/export matrix onto `can()` keys as a reviewable suggestion, never applied automatically. Every importer: idempotent via `external_refs` (source='sanoflow'), `--dry-run`, header mapping in a mapper file with unknown columns ignored, a counts-only report in `docs/audit/` (no names, phones or text), fixtures built synthetically in tests. Add a `pnpm import:sanoflow:all --dir=exports/ --org=<slug>` wrapper in the right order and wire its counts into `pnpm reconcile` and `pnpm cutover:preflight`. Also write `docs/audit/sanoflow-flow-inventory.md` as a template table (flow name, trigger, what it does, Pulse equivalent, rebuilt yes/no) for me to fill from the Sanoflow flow list."

## 20b: Flow parity (G2, G3, G4) · P1

> "Close the flow gaps in docs/20 §4 rows G2 to G4, inside the existing engine rules (rule 13: one job per step, advisory lock per conversation, 200 steps, every executor unit-tested; Dry run in `lib/flow-engine/simulate.ts` must cover each new node). **Triggers:** `message_received` (any inbound message on an open conversation, with keyword/source conditions, debounced so one burst starts one run), `window_closing` (fires N minutes before the 24 h customer-service window ends, scheduled through `scheduled_jobs`, cancelled when the customer writes again), `wa_flow_completed` (Meta Flow response webhook, payload stored as run variables), and make segment drip flows first-class in the builder and on the segment page. **Nodes:** `update_enquiry` (stage, status with lost reason, pipeline move, a field; emits the domain event exactly once), `payment_link` (wraps the Phase 19a provider, refuses when the integration is off or the org is in training), `meta_event` (wraps `buildCapiEvent()`, same consent rules), `set_label` (add/remove conversation label), `start_campaign` is NOT built (too risky from a bot: say so in the notes). **Question node:** answer types text, number, choice, phone, e-mail, date and regex; re-ask up to N times with a re-ask message, then the fallback edge; store to a run variable or contact field. **AI router node (draft-safe):** classifies the last inbound message into one of the node's intents using the existing closed-enum intent pipeline and routes to that edge; it never writes or sends model text itself; emergency wording still pre-empts it. Add each node to the catalogue, node schemas, Flow Copilot policy lists, labels, starter flows where useful, and the builder's checks (every option edge connected, one condition per branch, trigger connected). Tests: executor units, simulate runs, a race test for window_closing vs inbound reply."

## 20c: Routing and booking capacity (G5, G6) · P1

> "Teams and routing: add to teams an auto-reply message (sent once per conversation when a new chat lands in that team outside office hours or when nobody is online, only inside the 24 h window, through `queueOutbound`), a fallback team (used when nobody in the team is online or all are at capacity), and to members a `max_open_conversations` limit respected by round-robin; add presence auto-away after an org-level idle time (closes the docs/09 §2.3 presence gap) using heartbeats from the shell, not timers; add 'restrict enquiry view to own / team' per member, enforced in RLS, not only the UI. Booking capacity: services get buffer before/after, default duration and concurrent patients; specialists get slot length, max bookings per slot and recurring blocks by weekday. Put slot generation in one pure function in `lib/appointments/` used by the booking UI, waiting-list offers and the public API, and make `book_appointment` / `move_appointment` re-check capacity and buffers under the existing per-specialist lock. Unite stays read-only; when a Unite appointment conflicts with these rules show it, never refuse it. Tests: capacity races (two bookings for the last place), buffer edges across midnight and DST-free UAE time, routing when everyone is at capacity."

## 20d: Templates, campaigns, close-with-enquiry (G8, G9, G10) · P2

> "Templates: performance view per template and date range (sent, delivered, read, replied, button clicks, failed; from our own message statuses, plus Meta template analytics when the account allows it, unverified flag otherwise); per-template retry-on-fail and SMS-fallback switches (reuse Phase 19a SMS; utility and authentication only, never marketing); message TTL; carousel builder with live preview; URL-button and header variable mapping in the variable map. Campaigns: up to three retry rounds for failed recipients at chosen hour offsets, each round with its own funnel, skipping anyone who opted out or replied in between; recurring campaigns (cron with a readable summary, play/pause, audience re-evaluated each run, guardrails re-checked each run); CSV audience upload (parsed server-side, numbers to E.164, unknown columns ignored, file deleted after staging); a monthly message budget meter with a hard stop the admin sets. Inbox: extend the close dialog so a receptionist can, in one step, set the category and summary and create or update the linked enquiry (stage, status, lost reason, appointment request) through the existing enquiry actions and permissions. Tests for retry eligibility, recurring audience drift, the CSV parser and the combined close action's audit trail."

## 20e: Reports, channels, calendar (G7, G12, G13) · P2

> "Reports: add first-assign-to-close and last-assign-to-close times, owner removed, AI engaged and closed-without-human counts, a member status log (online/away/offline durations per day from the presence heartbeats), enquiry cohort by creation month, and template delivery/read/click rates, each registered in `lib/reports/registry.ts` with the shared filters and export. Channels: a website chat widget (embeddable script, per-domain allow-list, colours and welcome text in settings, visitors become contacts on first message, rate limited, no cookies beyond a session id) that lands in the same inbox; Instagram and Messenger through the Phase 19a integration foundation (item 6 of Prompt 19). Google Calendar: optional two-way busy sync per specialist (busy blocks in, Pulse appointments out as 'Busy' with no patient detail), OFF by default, behind the integrations catalogue with the typed confirmation words."

## Optional: REA deep dive on one Sanoflow screen (run locally, not in the repo session)

Use when a phase needs exact behaviour for something client-side (e.g. the AI agent node settings, a report's columns). Run in a separate Claude Code session on your machine with REA installed (`npx rea-agents@latest setup`) and a Chrome started with `--remote-debugging-port=9222` that you logged into yourself.

> "Using REA, attach to the Chrome target for app.sanoflow.io. I will open <SCREEN> and perform <ACTIONS>. Run `inspect_web_page` before, `observe_web_session` for 120 seconds while I click, and `inspect_web_page` after. Report only behaviour: fields, options, validation messages, defaults, which endpoints were called and with which parameter names, and state changes. Do not save or print response bodies, names, phone numbers or message text. Write the result as a short markdown note I can paste into docs/audit/sanoflow-<screen>.md, and keep REA's evidence bundle outside any git repository."
