# Soft delete with a restore window: notes

Closes the `docs/09` §2.3 Security gap "soft-delete with a restore window" (also §4.11, "Delete and merge exist"). Built in a cloud sandbox with plain Postgres 16; the UI was type-checked and linted but not driven in a browser.

Migration `supabase/migrations/20261120000100_soft_delete_restore.sql`; paste file `deploy/supabase-paste/60_soft_delete_restore.sql` (same SQL).

## What staff could hard-delete before, and what changed

| Record | Before | Now |
|---|---|---|
| Contacts (patients) | Already a soft delete (`deleted_at`, identifiers cleared), but no way back | Into the bin; restorable for the window; then made permanent (see Decisions 2) |
| Enquiries | Already a soft delete (`deleted_at`), no way back | Into the bin; restorable; then deleted |
| Tasks | Hard delete | New `tasks.deleted_at`; into the bin; restorable; then deleted |
| Website entry points (the only portal object with Delete) | Hard delete (and its portal tags) | New `website_entry_points.deleted_at`; into the bin; restorable; then deleted with its tags |

Deliberately left as they are: flows, templates (a delete also removes the template at Meta, which cannot be undone from Pulse), campaign drafts, segments, saved views, quick replies, tags, teams, roles, locations, services and other settings rows (configuration, audited, easy to recreate), time blocks, media library files and patient documents (Phase 16 has its own rules and retention), finance and accounting rows (their own controls: posted is permanent, month lock). The privacy erasure path (`erase_contact`, `privacy.manage`, two people) is untouched.

## How it works

| Part | Where | What it does |
|---|---|---|
| The bin | `public.deleted_items` | One row per soft-deleted record: org, entity (`contact`, `enquiry`, `task`, `website_entry_point`), record id, who, when, and for contacts the cleared identifiers (`restore_data`). RLS on, **no policies** (service role only; it holds phone numbers). Only records in the bin are listed, restored or purged |
| Delete | `public.soft_delete_records(org, entity, ids, actor)` via `lib/soft-delete/server.ts` `softDelete` | Called by `deleteContacts`, `deleteEnquiries` (`lib/enquiries/service.ts`), `deleteTasks` (`lib/tasks/service.ts`) and the portal `deleteRecord` (objects with `softDeleteEntity`). Only this org's live rows move; erased and merged contacts never do. Contacts: phone, WhatsApp id and Unite PIN are cleared as before (a new record can take them) and kept in the bin. Tasks: the finance links (claim follow-up stage, denial case, pre-authorisation expiry task) let go, as the old `on delete set null` did. Each action writes one `recordAudit` (`contact.deleted`, `enquiry.deleted`, `task.deleted`, `portal.record_deleted`, with `restorable: true` and counts) and the toast says for how many days it can be restored |
| Restore | `public.restore_deleted_record(org, entity, id, actor)`; action `restoreDeletedItem` (`app/(app)/settings/recently-deleted/actions.ts`) | Needs the record's own manage permission (`contacts.manage`, `enquiries.manage` plus the member's enquiry view, `tasks.manage`, `portal.website_entry_points.write`). Answers one word: `restored`, `not_found`, `expired` (past the window), `conflict` (a live contact now holds the phone, WhatsApp id or PIN; or the appointment already has an open call task), `parent_deleted` (its contact, or a task's enquiry, is still in the bin). Audited as `contact.restored`, `enquiry.restored`, `task.restored`, `portal.record_restored`. A restored open task gets its due reminder back |
| Window | `orgs.settings.soft_delete.restore_window_days`; `lib/soft-delete/rules.ts` and `app.restore_window_days()` | 30 days by default, whole days from 1 to 90. Set on the Recently deleted page by `security.manage` (`saveRestoreWindow`, audited `soft_delete.window_updated` with from and to). The TypeScript and SQL rules are the same (missing or non-number means 30, numbers are rounded and clamped) |
| Nightly purge | `public.purge_deleted_records(now, batch)`; task `soft_delete_purge` (`lib/jobs/handlers/soft-delete-purge.ts`); `pulse:soft_delete_purge` at 03:50 UTC | Takes at most 500 bin rows past their own org's window per call (oldest first, `for update skip locked`, so a restore in flight wins), up to 10 calls per run; idempotent; logs to `job_runs` (counts only) and writes one `audit_log` row per org, `deleted_items.purged`, with counts and the window |
| Recently deleted page | `/settings/recently-deleted` (Settings, Security & audit) | Open to anyone who can restore one kind of record, or holds `security.manage`. Lists only the kinds the member may restore, enquiries only inside their enquiry view, newest first: kind, title, who, when, days left, Restore. A list showing contacts writes a sampled `recordAccess` (`contact`, `list`) |
| Default reads | Policies `tasks_select`, `enquiries_select`, `website_entry_points_select` | Hide deleted rows; the matching UPDATE policies refuse a deleted row and refuse setting `deleted_at` from a browser. Server code (service role) filters `deleted_at` explicitly: task list, public API, enquiry drawer, reminders, front desk, end-of-day sheet, appointment call-task check, member off-boarding counts, finance follow-up completion, filter relations (`r.done = false and r.deleted_at is null`), portal list/count/ids/export/get/update/bulk (`compilePortalPredicate` adds `c.deleted_at is null` when the object has `softDeleteEntity`) |
| Erasure | Trigger `contacts_erase_soft_delete` | When `erase_contact` sets `erased_at`, the patient's bin row (and its copy of the old phone number) is deleted, so an erased patient can never be restored. A trigger rather than a change to `erase_contact`, so a later rewrite of that function cannot forget it |

## Decisions

1. **One bin table, `deleted_at` on the record.** `deleted_at` stays on each table (the filter every read already uses for contacts and enquiries); who and when, and the contact's cleared identifiers, live in `deleted_items`. That keeps merges (which also set `contacts.deleted_at`) and erasure (which sets it too) out of the bin without new flags, and gives the page and the purge one place to look. Records deleted before this release have no bin row: they are neither listed nor purged (unchanged).
2. **A contact is not hard-deleted at the end of the window.** Conversations, messages, appointments, visits and prescriptions point at the contact row (some with `on delete cascade`, one with `restrict`), and removing a patient's details is the two-person erasure. So the purge only drops the bin row (and its copy of the phone number); the contact stays the hidden tombstone it always was after a delete. Use Patient data requests to erase.
3. **`contacts_select` is unchanged.** Inbox, appointments and history legitimately show merged, erased and deleted patients through joins; hiding them by policy would break those screens. Contact lists, search and matching already filter `deleted_at`.
4. **Unique keys.** Contacts: the partial unique indexes already ignore deleted rows and the identifiers are cleared at delete, so a new contact can take the number; restoring over a live holder is refused (`conflict`), never merged silently. Tasks: `tasks_open_call_per_appointment_uidx` now ignores deleted tasks (a deleted call task no longer blocks the reminder handler raising a new one); restoring over an open one is refused. Website entry points: the `(org, section, source)` constraint still covers deleted rows on purpose (the Airtable importer upserts on it), so re-creating the same entry point while the old one is in the bin fails with "it may be in Settings, Recently deleted: restore it instead".
5. **Purging an enquiry keeps its tasks and the patient's timeline.** `tasks.enquiry_id` and `timeline_events.enquiry_id` cascade on delete, so the purge clears those links first; the tasks (live or in the bin) and timeline entries stay. Field-level history (`record_history`) of a purged task or enquiry stays, as it did for hard-deleted tasks.
6. **Parents first.** A task or enquiry whose contact is in the bin (or a task whose enquiry is) cannot be restored until the parent is, so nothing comes back pointing at a hidden record.
7. **Not relinked.** A restored task is not linked back to a finance follow-up, denial case or pre-authorisation (the finance job raises its own); a due reminder that fell while the task was in the bin is not resent.
8. **No new permission.** Restoring needs the record's own manage key; the window is a security setting (`security.manage`).

## Tests

- `tests/db/soft-delete.test.ts`: moves only this org's live rows and frees contact identifiers; deleted rows are invisible to normal reads, the bin is service-only and a browser cannot edit or soft-delete around it; restore puts identifiers back; parents first; clashes refused (phone, open call task); window per org (expired, then allowed with a longer window); cross-org restore refused; purge removes only rows past each org's own window, keeps an enquiry's tasks and timeline, keeps the contact row, removes entry point tags, writes one audit row per org and is idempotent; erasure still erases and removes the bin row; the three functions are service-role only.
- `tests/unit/soft-delete.test.ts`: window read/write/validation (same rule as SQL), days left, entity permissions, page access and Settings entry, messages, portal predicate.
- `tests/db/security-guard.test.ts`: `deleted_items` is in the service-only list and seeded (`seedSoftDeleteRows`); `tests/db/jobs.test.ts`: the new cron job.
