# Phase 19b notes: Google review requests, Meta ad attribution, video visits, e-signature

Built on branch `claude/nifty-brown-y9l5ry` (from `main` at `8849b35`, Phases 13 to 19a merged), 19 Oct 2026 session. Spec: `docs/10_NEXT_PHASE_PROMPTS.md`, Prompt 19, candidates (4) Google Business review requests, (5) Meta ad attribution and Conversions API, (8) telehealth link on a video appointment type and (9) e-signature for consent forms, all on the Phase 19a foundation (`docs/18_PHASE_19A_NOTES.md`, "How to add the next integration"). With 19a this completes Phase 19 except candidate (6), the Instagram and Messenger inbox, which is not built. Candidate (7), the accounting export, was built in Phase 18.

Built in a cloud sandbox with a plain Postgres 16 (pgvector, PostgREST), no browser, no Supabase Auth or Storage stack and **no real provider of any kind**: every adapter is tested against fake `fetch` functions that return responses written from the providers' documentation, and `tests/setup.ts` now also makes any `fetch` to `daily.co`, `hellosign.com` and `dropboxsign.com` throw (Meta's Graph host was already blocked).

**All four are OFF by default** (`integration_accounts.enabled = false`). Review requests, video visits and e-signature need a typed confirmation to switch on, and so does Meta ad attribution (it shares data); none of them does anything in a training workspace.

## NOT verified

- **No real provider was ever called.** Meta's Conversions API (the business-messaging payload: `action_source: "business_messaging"`, `messaging_channel`, `user_data.whatsapp_business_account_id` and `ctwa_clid`, whether Contact, Lead and Schedule are accepted event names for a WhatsApp dataset, `test_event_code`, the bearer header, the response and error codes), Daily's room API (`nbf`, `exp`, `eject_at_room_exp`, the "already exists" answer), and Dropbox Sign's API v3 (`signature_request/send` with JSON and `file_urls`, text tags, `expires_at`, the cancel call, `files_as_data_uri`, the callback format, the event hash, the plain-text acknowledgement) all come from documentation as the author knows it. **Each must be checked against a sandbox or test account before anything is switched on** (OQ-87 to OQ-89). The Meta payload shape in particular needs checking against the current Business Messaging documentation.
- **No Google check of the review links** beyond their shape, and no check that Google accepts a WhatsApp invitation of this kind; no WhatsApp: the template was queued and inspected, never approved or delivered.
- **No browser, no phone.** The settings pages, the review links panel, the CAPI consent panel, the ad report, the Join buttons, the visit type on services and appointments, the "Do not ask" switch and the e-signature section were typechecked, linted and built, not clicked.
- **No real storage service.** The e-signature database tests use an in-memory storage port; `probeObject`, signed upload URLs and the private buckets were not exercised for the signed copy (the same code paths as uploads in Phase 16, which were tested the same way).
- **Video quality, joining from a phone, the meeting service's own settings** (waiting room, recording defaults) are untested; with the generic address option Pulse cannot end a room or stop recording.
- **pg_cron** for the four new schedules (the harness has a stub; the statements of `housekeeping_19b` were executed by hand from `cron.job`; the other three are `app.ping_jobs` calls like earlier phases).
- **Performance at volume**: the sweeps read at most 500 rows per organisation per run; unmeasured beyond clinic volumes.

## Decisions and deviations worth knowing

1. **Review requests are not filtered by satisfaction, complaints or AI tags.** The brief first asked for a sensitivity filter on complaints and emergencies, then to stay inside Google's policy (no review gating). The second won: the only filters are consent, the staff "Do not ask" switch, test and erased records, training mode, and having a link. A patient who complained can therefore be asked. If the clinic wants to avoid that for care reasons, staff tick "Do not ask" (a conversation or task tag is deliberately not read). **There is no "deceased" field in Pulse**; the same switch covers it (OQ-86).
2. **Opt-in means `promotions_opt_in` and not `stop_marketing`**, checked for the person messaged (the guardian of a dependant) and for the patient. The cap covers the patient and the person messaged, so a parent of three children is asked once; it is claimed in the database (`claim_review_request`, advisory locks), not in application code.
3. **Review requests ride the existing `appointments` queue** (kinds `review.send`, `telehealth.cleanup`) instead of a new queue; Meta events have their own queue because they retry with back-off and must not delay reminders.
4. **Ad attribution records clicks only while the integration is on**, and starts in "report only" mode, so switching it on stores click ids but sends nothing until an administrator chooses "send events" and enters credentials. The mapping Contact = first message from an ad, Lead = an enquiry for that patient, Schedule = a booking for that patient within the window is Pulse's own reading (OQ-87). An e-mail is never sent (the builder can hash one; the server passes none); a hashed phone is off by default.
5. **The consent basis for ad events** is `contact_opt_in` (default) or `admin_declared`, the second set by a separate action that needs the sentence "I CONFIRM AD MEASUREMENT BASIS" and records who and when; a stop is honoured under both.
6. **Video room tokens are stored encrypted, not only hashed**, because staff must be shown the link again and reminders must carry it; the SHA-256 is kept for lookup and audit. The table has no policy at all (service role only). A room is created lazily (first Join, or a message that uses the variable), never in bulk, and rooms for static addresses cannot be ended by Pulse.
7. **The video link is a template variable, not a second set of video templates.** A clinic maps one variable of its reminder template to "Appointment: video visit link"; for an in-person visit that variable says "at the clinic". Separate `reminder_video` / `confirmed_video` template keys were considered and not built.
8. **The signer's e-mail is typed by staff for each request and is not stored** (only `s***@example.com`); the signer's name is also sent. Prefilled from the contact for convenience. A provider that signs by phone would need a different adapter (the interface allows it; this one refuses a signer without an e-mail).
9. **E-signature test mode is on by default** so the first requests are free and non-binding; an administrator turns it off after seeing a signed copy arrive. The consent PDF must carry the provider's signature tags.
10. **The provider's callback is not replay-windowed** (providers retry for hours); safety comes from the event hash, the idempotent claim per event, the forward-only status and the fact that "signed" always re-fetches the file with the API key.
11. **A signed request whose file cannot be stored is still marked signed**, with `error_code` set and a message in the Documents tab telling staff to download it from the provider; a temporary failure answers 500 so the provider retries.
12. **The generic template panel** (`TemplateMapPanel`) replaced the payment-only one; payments behave as before.
13. **The hub shows a "Shares data" badge** for integrations that send patient-derived data to a third party (Meta ad attribution and e-signature).

## Before first use on the real stack

1. Apply `deploy/supabase-paste/19b_phase_19b_integrations.sql` to the **Pulse** project only (check the project name first), after the 19a file, or `supabase db push`. Custom roles need `ads.view` added by hand if wanted.
2. Settings, Integrations: for each integration enter the settings, press Save and Test connection, then switch on with the typed words. Start Meta in **Report only**; keep e-signature in **Test mode**; try video with a colleague.
3. Reviews: create and get approved a WhatsApp template with the link as a body variable, choose it and map its variables, paste each location's Google review link. Review requests start with visits that finish after the switch.
4. Meta: create a test event code in Events Manager, send a few events with it, check them, then clear it.
5. Video: mark a service as Video (Settings, Appointments) and map a template variable to the video link.
6. E-signature: give the provider the callback address shown on the page; prepare the consent PDFs with the provider's signature tags; send yourself a request.
7. System health shows each integration; look there after the first real call.
