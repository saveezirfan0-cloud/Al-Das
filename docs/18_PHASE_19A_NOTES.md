# Phase 19a notes: integrations foundation, doctor calendar feeds, SMS fallback, payment links

Built on branch `claude/nifty-brown-y9l5ry` (from `main` at `6484c13`, Phases 13 to 18 merged), 18 Oct 2026 session. Spec: `docs/10_NEXT_PHASE_PROMPTS.md`, Prompt 19, for candidates (1) calendar ICS feed, (3) SMS fallback and (2) payment links, plus the shared foundation every later integration (Phase 19b) will reuse. Built in a cloud sandbox with a plain Postgres 16 (pgvector, PostgREST), no browser, no Supabase Auth stack and **no real provider of any kind**: every adapter is tested against fake `fetch` functions that return responses written from the providers' documentation. `tests/setup.ts` now makes any `fetch` to Stripe, PayTabs or Twilio throw.

**All three integrations are OFF by default** (`integration_accounts.enabled = false`). SMS and payment links also need a typed confirmation to be switched on, and neither works in a training workspace.

## What exists

| Spec item | Where it lives | What it does |
|---|---|---|
| **Credentials and on/off flag** | `integration_accounts` (the Finance F2 table, extended in migration `…100`); `lib/integrations/accounts.ts`, `catalog.ts` | One row per (workspace, kind). Secret fields are encrypted into `config_enc` (AES-256-GCM, `lib/crypto.ts`); other settings are plain JSON in `config`; `enabled` defaults to false. The table keeps **no policies** (it holds ciphertext): only server code reads it after `can()`, and `loadView()` / `toView()` give pages only "is each secret stored" |
| **Typed client base** | `lib/integrations/client.ts` with `backoff.ts` and `breaker.ts` | https only and a per-adapter host allow-list, a timeout and response cap on every call, no redirects, exponential back-off with jitter (honours `Retry-After`), a circuit breaker (opens after 5 provider failures in a row, 5 minute cool-down, then a probe) whose state is stored in `integration_accounts.consecutive_failures / breaker_open_until`. Idempotent requests are retried; a POST without an idempotency key is retried after a 429 only, and after a timeout or 5xx it is reported `ambiguous` so nothing can send it twice |
| **Call log without bodies** | `integration_calls` (30 days) | One row per attempt: provider, operation, outcome, status code, latency, attempt number. Never a URL, header, body, number, link or amount (a unit test searches the log for planted secrets) |
| **Inbound webhook helper** | `lib/integrations/webhook.ts` (constant-time compare, replay window, HMAC) and `webhook-route.ts` (`receiveIntegrationWebhook`) | 404 for an unknown or switched-off account (the same answer), 413 over 256 KB, signature check, per-IP limit on failures and a per-account limit, then every event claims its key in `integration_webhook_events` before it acts; a repeat is skipped; a failing handler releases the claim and answers 500 so the provider retries |
| **Health on System health** | `lib/integrations/health.ts`, `health-server.ts`, a new card on `/settings/system-health` | Off / not used yet / healthy / some failures / failing, from the last 24 hours of calls, the breaker and the last error. Also shown on the hub |
| **Settings, Integrations** | `/settings/integrations` (hub) and `/settings/integrations/<kind>`; `integrations.manage` (Admin only) | A card per integration with its state; each page has the status, the switch (typed words for SMS and payments), the settings form (secrets are write-only), Test connection (a read-only call), the webhook address to give the provider, and 30-day counters |
| **(1) Doctor calendar feeds** | `lib/integrations/calendar/*`, `app/api/calendar/[token]/route.ts`, the Calendar panel; `integrations.calendar` | A private `.ics` link per doctor, or "my appointments" for a person (every doctor profile linked to them). 256-bit token, only the SHA-256 stored, link shown once, rotate and revoke. Events carry a hashed id, start, end, the title "Appointment" and the location name, nothing else. Last 7 days and next 60. Cancelled appointments stay as `STATUS:CANCELLED` with a higher `SEQUENCE`. Rate limited per IP and per token; the same 404 for unknown, revoked, malformed and switched-off. Access is an aggregate counter, not a per-request record |
| **(2) SMS fallback** | `lib/integrations/sms/*`, `lib/jobs/handlers/sms-outbound.ts`, migration `…300`; adapter `twilio.ts` | When an appointment reminder fails permanently on WhatsApp, `reportReminderFailure()` also calls `queueSmsFallback()`: it picks the recipient with `resolveRecipient()` (a child's reminder goes to the guardian), applies `smsDecision()` (mobile number, no SMS opt-out, not WhatsApp error 131050, appointment still ahead), writes one `sms_messages` row (deduped per reminder) and puts it on the **`sms_outbound` queue**. The queue handler sends it with a per-sender rate limit, a daily limit and every guard checked again. Fixed generic wording only. Delivery receipts arrive at a signed webhook and move the status forward only. Counters: queued, sent, parts, delivered, failed, unsubscribed, skipped by reason, blocked (training, daily limit), plus an estimated spend if a price per part is entered |
| **(3) Payment links** | `lib/integrations/payments/*`, `app/(app)/finance/payment-links`, migration `…400`; adapters `stripe.ts`, `paytabs.ts`; `finance.payment_links` | From a finance invoice: find it by number, check the amount (never more than the invoice total), tick the check, send. The gateway creates the link; the patient (or guardian) gets it as an **approved Utility WhatsApp template** through `queueOutbound`. One open link per invoice; link life up to 24 hours; cancel closes it at Stripe. `fin_payment_requests` holds PIN, invoice number, amount in minor units, currency and the gateway's status: no names, no card data, not the link. The webhook records paid / failed / expired, **never applies a payment whose amount or currency differs** (it flags the request and tells finance), records a payment that arrives after the link was closed as paid but flagged, and **never marks the invoice as paid or writes anything to Unite** |

New permissions: `integrations.manage` (Admin only), `integrations.calendar` (granted to the Manager preset) and `finance.payment_links` (Finance and Billing presets); the data migration grants them to existing system roles once, idempotently, and a database test proves it. Migrations `20261018000100` to `…400` add six tables (`integration_calls`, `integration_webhook_events`, `integration_usage_daily`, `calendar_feeds`, `sms_messages`, `fin_payment_requests`), the `sms_outbound` queue, `contacts.sms_opt_out_at`, three service-only functions and four schedules (`sms_outbound` every 10 s, `sms_stalled` every 10 min, `fin_payment_expiry` every 15 min, `housekeeping_integrations` daily). No new environment variable: provider credentials live in the database, encrypted.

### Other changes outside the new files

`lib/jobs/handlers/appointments.ts` (`reportReminderFailure` calls the SMS fallback after raising the call task; the call task stays as the human safety net), `lib/jobs/queues.ts`, `lib/rate-limit.ts` (new rules), `lib/supabase/middleware.ts` (`/api/calendar` and `/pay/done` are reachable without signing in), `lib/security/policy.ts` (three new unauthenticated routes with their reasons), `components/shell/settings-pages.ts`, `nav.ts`, `lib/finance/nav.ts`, `lib/help/guides.ts` (two guides), `lib/help/whats-new.ts`, `tests/setup.ts`, `tests/db/helpers.ts` (`PHASE19_TABLES`, `seedPhase19Rows`), `lib/supabase/types.ts`. `app/pay/done/route.ts` is a static "thank you" page for the patient after paying (Stripe requires a return address; PayTabs returns the patient with a POST); it reads nothing and shows nothing.

What the tests cover:

- **Client base** (fake clock, fake `fetch`): host and https guard, retries with the expected sleeps, no retry of a POST after 5xx or timeout (ambiguous), retry after 429 with `Retry-After`, response cap, a failing log sink or breaker store never breaks a call, the breaker opens at the threshold and refuses without calling, half-open probe, a 4xx does not count; the call log contains only its six fields and none of the planted secrets.
- **Webhook signatures**: Stripe (tamper, wrong secret, 5 minute replay window both ways, several `v1` values), PayTabs, and Twilio against the example published in Twilio's documentation.
- **ICS**: escaping, folding at 75 octets without splitting Arabic characters, CRLF, UTC, stable UID, increasing `SEQUENCE`, cancelled events, the window, an exact allow-list of properties, hostile extra fields never appearing in the output, a minimal reader that unfolds and checks the structure.
- **SMS**: GSM-7 and UCS-2 part counts at the boundaries, the fixed wording in English and Arabic, no name except a guardian's child, every consent rule (including "a marketing opt-out does not stop a reminder" and "marketing needs the opt-in"), the status ladder (property-tested against the SQL-friendly `previousStatusesFor`), the Twilio-style adapter with recorded responses (success, unsubscribed 21610, bad number, auth, 5xx, timeout, 429).
- **Payments**: money parsing without floating point, every branch of the payment state machine, Stripe and PayTabs adapters with recorded responses (fields sent, idempotency key, no names, 4xx codes, retries), webhook parsing for every event type.
- **Database**: cross-org isolation and the permission matrix for all six tables, browsers can never write any of them, constraints (one live request per invoice, unique references, cross-org parents), the four scheduled statements executed from `cron.job`, the permission data migration; and through PostgREST the whole flow: feeds (window, privacy, rotate, revoke, 304, counters), SMS (queue, dedupe, send, guardian, opt-out, landline, cancelled meanwhile, permanent, ambiguous and retryable failures, rate limit, daily limit, training mode, the real failed-reminder path), receipt route (bad signature, unknown account, duplicate, unsubscribe), payments (guards, link creation, message values, one live link, invoice untouched, signature, stale timestamp, wrong account kind, amount mismatch, replay, late payment after cancel, handler failure releasing the claim, rate-limited bad signatures).
- **Static**: `pnpm audit:security` and `tests/unit/security-static.test.ts` see the new actions and routes; `tests/unit/integrations/catalog.test.ts` checks that integration code never imports Unite or writes invoices, never calls bare `fetch`, never logs bodies or links, keeps secrets out of client components, and that every server action starts with `requirePerm`.

## NOT verified

- **No real provider was ever called.** Twilio, Stripe and PayTabs request and response shapes, header names, the PayTabs callback fields and statuses, the Stripe event names and the PayTabs region hosts all come from documentation as the author knows it. **Each must be checked against a live sandbox account before anything is switched on.** In particular PayTabs: the signature header name, whether `tran_total` includes fees (a difference would show as "needs review", the safe failure), and that the hosted page has no expiry parameter (Pulse enforces expiry itself and records a late payment as flagged).
- **No calendar app.** The ICS output is checked structurally by a small reader in the tests and was not opened in Outlook, Google Calendar or Apple Calendar. Subscription refresh timing is up to each app.
- **No browser, no phone.** The hub, the integration pages, the calendar panel, the payment template mapper and the Payment links page were typechecked, linted and built, not clicked.
- **No WhatsApp.** The payment message was queued and inspected; no template was approved by Meta. Meta may classify a payment-request template as Marketing, which the settings page refuses (Utility only) but cannot predict.
- **No SMS to a UAE number.** Sender-ID registration, delivery to UAE networks and the receipt statuses a UAE route reports are unknown.
- **Types** were generated from the test database with the Supabase CLI and formatted with Prettier, and only the Phase 19a hunks were merged into `lib/supabase/types.ts` (the committed file differs from fresh output in relationship ordering from earlier phases). Run the drift check on a real stack.
- **pg_cron** for the four new schedules (the harness has a stub; the statements were executed by hand from `cron.job`).
- **Performance** at volume: the call log is one insert per attempt; fine for clinic volumes, unmeasured at thousands per minute.

## Decisions and deviations worth knowing

1. **`integration_accounts` stays service-only (no policy)** instead of getting an org policy. It holds ciphertext and the existing Finance and Unite code already depends on it being server-only; settings pages use the service role after `requirePerm('integrations.manage')` and see no secret. Every new table that a person may read (`integration_calls`, `integration_usage_daily`, `calendar_feeds`, `sms_messages`, `fin_payment_requests`) has an `org_id` policy; `integration_webhook_events` and `integration_accounts` are in the service-only list of the security-guard test with reasons.
2. **The switch lives on each integration's page**, not on the hub cards (the hub shows state and links). Switching on needs `integrations.manage`; managing feeds needs `integrations.calendar` and nothing else; an administrator with only `integrations.manage` (not `*`) can switch calendar feeds on but cannot create a feed.
3. **The call task stays when an SMS is queued.** Reception still gets the "call the patient" task for a failed reminder; the SMS is an extra attempt. Closing the task automatically on a delivered SMS is a one-line follow-up once the clinic says it wants it.
4. **A guardian's SMS names the child by first name.** The brief said no names; the Phase 14 household rule says a message about an appointment must say whose it is. Only first names, only for guardian-addressed messages (OQ-84).
5. **An ambiguous SMS failure is never retried.** After a timeout or 5xx the provider may already have sent it, so the message is marked failed (`unknown_delivery`) rather than risk a double text; the call task covers the patient.
6. **No staff switch for "do not SMS this patient" yet.** `contacts.sms_opt_out_at` exists and is set when the provider reports an unsubscribe (Twilio 21610) and honoured everywhere, but there is no button on the patient card. Until one exists, an opt-out told to reception by phone has to be set in the database (OQ-84).
7. **Payment amount check is against the invoice total, not the outstanding balance.** Payments already received are not subtracted, so staff must check the amount themselves (the page says so). Subtracting needs the F2 payment mapping to be proven.
8. **Payment links use Stripe Checkout Sessions, not Payment Links**, because a Checkout Session can expire (Stripe allows up to 24 hours) and can be closed from Pulse. PayTabs links cannot be closed by Pulse; a payment on a cancelled PayTabs link is recorded and flagged.
9. **A late payment is recorded as paid but flagged**, not refused: the money exists. Mismatched amounts are not recorded as paid at all.
10. **`fin_payment_requests` survives patient erasure** (the contact id is nulled; PIN and invoice number stay, like the rest of finance). Say so in the retention policy (OQ-64/65).
11. **Half-open breaker lets concurrent callers probe.** Single-probe locking would need an atomic claim; with these volumes the cost of two probes is nil.
12. **Test connection exists for Twilio and Stripe only.** PayTabs has no read-only call Pulse is sure of; the page says to make a small payment in the gateway's test mode instead.

## Before first use on the real stack

1. Apply `deploy/supabase-paste/19a_phase_19a_integrations.sql` to the **Pulse** project only (check the project name first), after the Phase 18 file, or `supabase db push`. Custom roles need the new keys added by hand.
2. Settings, Integrations: for each integration enter the keys, press Save and Test connection, then switch on. Do SMS and payments against the provider's sandbox or a number the clinic owns first.
3. Payments: create and get approved a **Utility** WhatsApp template with the link in its body, choose it under Payment message and map its variables. Give the gateway the webhook address shown on the page.
4. SMS: register the sender ID, enter the clinic name and the number patients should call, and keep the daily limit low for the first week.
5. System health shows each integration; look there after the first real call.

## How to add the next integration (Phase 19b)

1. **Catalogue.** Add the kind to `INTEGRATION_KINDS` and an entry to `INTEGRATIONS` in `lib/integrations/catalog.ts`: title, who may see it (`viewPermission`), `outbound`, `contactsPatients` / `movesMoney` (these decide the typed `confirmWord`), providers with their fields (`secret: true` puts a field in the encrypted blob), common fields and the one-sentence consequence. Add its adapter ids to `CALL_PROVIDERS` in `lib/integrations/health.ts` so health counts its calls. Add readiness rules to `lib/integrations/readiness.ts` (what must be true before it can be switched on).
2. **Permission.** Add the key to `lib/auth/permissions.ts` and, for existing workspaces, a `do $$ … $$` grant block like the one in `…100`; extend the permission data-migration test if the grant is not the default.
3. **Adapter.** Write a small module that builds a client with `createIntegrationClient({ provider, allowedHosts, fetchFn, sink, breaker })` (pass `dbCallSink` and `dbBreakerStore` from `accounts.ts` in the server factory), takes an injected `fetchFn`, never logs a body, and maps provider answers to a small result type. Mark a POST `idempotent: true` only if the provider honours an idempotency key. Add a fake next to it and recorded responses to its test; add the provider's host to the block list in `tests/setup.ts`.
4. **Inbound.** Write a `WebhookSpec` (`verify` with the primitives in `lib/integrations/webhook.ts`, `parse` to events with a stable key, `handle` that returns a short outcome word), add `app/api/webhooks/integrations/<kind>/[accountId]/route.ts` calling `receiveIntegrationWebhook`, and an entry in `UNGUARDED_OK` in `lib/security/policy.ts` with the reason.
5. **Data.** New tables: RLS and an `org_id` policy (or a service-only entry with a reason in `tests/db/security-guard.test.ts`), added to `PHASE19_TABLES` and `seedPhase19Rows` (or a new `PHASE19B_*` pair) in `tests/db/helpers.ts`; cross-org tests like `tests/db/integrations-rls.test.ts`. Count usage with `bumpUsage(admin, orgId, kind, metric)`.
6. **Sending anything to a patient.** Only through `queueOutbound` (approved template, `resolveRecipient`, consent flags) or the SMS queue; refuse a training workspace (`isTrainingOrg`); check `isEnabled()` first on every path; make the first send a person's explicit action.
7. **UI.** The generic hub and `/settings/integrations/<kind>` render from the catalogue; kind-specific panels are added in `[kind]/page.tsx` (see the Calendar and Payment message panels). Register nothing in `settings-pages.ts`: the hub entry already covers it. Add a help guide and a what's-new line.
8. **Server actions.** `requirePerm` first, `recordAudit` (ids and field names only), rate limit anything unauthenticated, redact free-form errors with `lib/redact.ts`, and keep `"use server"` files to async exports.
